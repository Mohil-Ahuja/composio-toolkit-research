The agent

Three model loops and two loops with no model in them

The interesting design decision was not the prompt. It was noticing which questions a language model is bad at and taking those away from it.

Loop 1 · control

Parametric baseline

Claude Opus 5, no tools, answering from weights. Never shipped — it exists to be graded, so the retrieval has something to beat.

→ pass1_baseline.json
Loop 2 · retrieval

Primary-doc grounding

One app per request with server-side web search and fetch, structured JSON out, every field carrying a URL the model actually opened. "Not stated in the docs" is a legal answer.

→ 100 records + evidence
Loop 3 · adversarial

Attack the weakest field

A fresh request that never sees loop 1, told to find the field most likely wrong rather than to double-check. Asking a model to review its own work mostly produces agreement.

→ disagreements.json
Loop 4 · deterministic

Endpoint probe

73 candidate MCP URLs fetched directly. A page counts only if it returns 2xx and the body actually discusses MCP — docs sites happily return 200 for paths that don't exist.

→ mcp_probe_results.json
Loop 5 · deterministic

Catalogue diff

All 100 checked against Composio's public toolkit pages, then ranked by how little stands in the way, which is what turns a spreadsheet into a queue.

→ composio_gap.json

Where a human was needed

  • Deciding what "self-serve" meansVendors never phrase it. A 14-day trial that issues a token and an enterprise contract that issues one look identical in the docs. The four-level scale is a judgement call I made and wrote down, so a reader can disagree with the rule rather than the rows.
  • Disambiguating ConsensusThe brief points at consensus.app, the academic search engine. The first search returned goconsensus.com, an unrelated demo-automation vendor whose API is Enterprise-only. Two different answers, both well-sourced, for one row.
  • Following the fanbasis redirectfanbasis.com 301s to commas.com — a July 2026 rebrand — and the API reference lives on a third domain, apidocs.fan. The baseline called this "no public API". The redirect was machine-detectable; knowing it mattered was not.
  • Refusing to fill a gapPaygent Connect produced nothing under that name across three searches. It stayed unknown with confidence low. A plausible guess would have been worse than a blank.
  • Reading a 404 as a signalClickUp's missing docs page still carried 36 mentions of MCP, which meant the docs existed elsewhere. Four rows were corrected that way — the probe found the smoke, a person went looking for the fire.

The part that matters

How much of this would have been wrong without the loops

22 apps were verified by hand against two or more independent sources, spanning all ten categories and deliberately over-weighted toward the rows most likely to break: long-tail vendors, recent rebrands, ambiguous gating. Five graded fields per app, 110 judgements per pass. It is a harder-than-average sample, which makes these numbers a floor, not a flatter.

What I still don't trust

    Known limits of this dataset

    • The gold sample is stratified, not randomIt over-samples hard rows on purpose, so it measures the long tail better than it measures Stripe and GitHub. A uniform random sample would score higher and tell you less.
    • Access is a judgement, not a factFour buckets over a messy reality. Squarespace gates by plan and by API; Otter's MCP is free while its REST API is enterprise-only. Those rows are true but lossy, and the note field carries what the bucket drops.
    • 32 rows rest on a single vendor pageMarked medium confidence. They are the most likely place a second reviewer would find an error, and they are labelled so nobody has to guess which ones they are.
    • Bot-blocked vendorsPitchBook, Otter, Grain, Consensus and Salesforce returned 403 to automated fetches at least once. Those answers lean on help-centre mirrors and search synthesis, which is weaker evidence than a vendor doc read directly.
